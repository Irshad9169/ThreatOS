Linux Servers — How It Works Today
What runs where:
Each Linux server you want to monitor:
  └── syslog_forwarder.py  (small Python script, runs as systemd service)
      │
      ├── Reads:  /var/log/authlog    (SSH, sudo, PAM)
      ├── Reads:  /var/log/messages   (system events)
      ├── Reads:  /var/log/cron       (scheduled tasks)
      ├── Reads:  /var/log/audit/audit.log
      └── Reads:  /var/log/nginx/access.log
      │
      └── Sends batches to → http://test06:8001/api/ingest/batch
                             (using API key for authentication)
Currently monitoring:

test06.hyd.int.untd.com — the ThreatOS server itself ✅

To add any other Linux server (5 minutes work):
bash# On the new Linux server
scp root@test06:/opt/threatos/scripts/syslog_forwarder.py /opt/

# Create the service
cat > /etc/systemd/system/threatos-forwarder.service << 'EOF'
[Unit]
Description=ThreatOS Syslog Forwarder
After=network.target

[Service]
Type=exec
Environment="THREATOS_URL=http://test06.hyd.int.untd.com:8001"
Environment="THREATOS_API_KEY=<REDACTED_API_KEY>"
ExecStart=/usr/bin/python3 /opt/syslog_forwarder.py
Restart=always

[Install]
WantedBy=multi-user.target
EOF

systemctl enable --now threatos-forwarder
# Done — that server is now monitored

      Same API key auth

      OPTION B: Windows Event Forwarding (WEF)
      ─────────────────────────────────────────
      Windows built-in feature — no agent needed
      Collector server receives events from all Windows machines
      Collector forwards to ThreatOS

Where Logs Are Stored
Raw events — PostgreSQL:
sqlTable: raw_events
  id           UUID
  received_at  TIMESTAMPTZ    ← when ThreatOS received it
  log_source   VARCHAR        ← "syslog-auth", "winlog", "nginx" etc
  hash         VARCHAR        ← SHA256 for deduplication
  normalized   JSONB          ← parsed fields: host, user, process,
                                 command_line, src_ip, message...

Retention: 90 days (auto-deleted by retention worker)
Current size: ~3.5MB for test06 logs
Alerts — PostgreSQL:
sqlTable: alerts
  technique_id  VARCHAR   ← T1059.004
  tactic        VARCHAR   ← execution
  risk_score    FLOAT     ← 73.5
  entity_host   VARCHAR   ← test06.hyd.int.untd.com
  entity_user   VARCHAR   ← root
  status        VARCHAR   ← open/investigating/closed/false_positive
  ti_verdict    VARCHAR   ← malicious/suspicious/clean (after TI enrichment)

Retention: 365 days
NOT stored — what gets discarded:

Duplicate events (same hash within dedup window)
Events older than 90 days (raw_events)
Benign events that don't match any rule (they're evaluated then discarded)


The Key Point for Your Manager
Tell your manager this:

"Every Linux server in our environment needs a small Python script installed — about 50 lines of code — that reads the existing system logs and forwards them to ThreatOS. The logs already exist on every server. We're just reading them and sending them over the network.
For Windows servers, there are two options: install a free agent like NXLog, or use Windows' built-in Event Forwarding feature. Either way, the 2,641 Windows detection rules we already have will start working automatically the moment Windows events start flowing in.
All logs are stored in our own PostgreSQL database on test06, retained for 90 days for raw events and 1 year for alerts. Nothing goes to any external service. The only external calls are to VirusTotal and AbuseIPDB for threat intelligence lookups — and those only happen when we explicitly enrich an alert."
