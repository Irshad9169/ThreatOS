1. How Prometheus + Grafana Works
ThreatOS Server (test06)          Remote Machine (test05)
─────────────────────────         ───────────────────────
FastAPI :8001                     Prometheus :9090
  └── /metrics endpoint  ◄──────── scrapes every 15s
      exposes 18 metrics           stores time-series data
                                        │
                                        ▼
                                   Grafana :3000
                                   reads from Prometheus
                                   draws charts + dashboards
                                   sends alerts if thresholds hit
The flow in plain English:

ThreatOS exposes a /metrics URL that lists current counts
Prometheus visits that URL every 15 seconds and records the numbers
Grafana reads Prometheus and draws them as charts over time
You can set alert rules in Grafana — e.g. "notify me if open alerts > 5"

What each ThreatOS metric means in Grafana:
threatos_alerts_created_total
  → Rate of new alerts over time
  → Spike = something is being detected
  → Zero for hours = no events coming in (pipeline broken)

threatos_worker_lag_events
  → How many events are waiting to be processed
  → Should always be near 0
  → If it grows = worker is overwhelmed or crashed

threatos_http_request_duration_seconds
  → API response times
  → p95 > 2s = something is slow, investigate DB or pool

threatos_attck_coverage_percent
  → Should stay at 100% — drops if rules get bulk disabled

threatos_rules_loaded_total
  → Should match rules_enabled_total
  → Gap between them = engine didn't reload after rule change

threatos_alerts_by_status{status="open"}
  → Current open alert count
  → Set Grafana alert: if > 10 for 5 minutes → send notification

threatos_db_pool_checked_out / threatos_db_pool_size
  → DB connection pool usage %
  → If consistently > 80% = add more pool connections or PgBouncer
  
Setting up Prometheus alerts (on test05):
yaml# Add to prometheus/alerts.yml
groups:
  - name: threatos
    rules:
      - alert: WorkerLagHigh
        expr: threatos_worker_lag_events > 1000
        for: 2m
        labels:
          severity: critical
        annotations:
          summary: "ThreatOS worker lag too high"
          description: "{{ $value }} events pending"

      - alert: NoEventsIngested
        expr: rate(threatos_events_ingested_total[1h]) == 0
        for: 2h
        labels:
          severity: warning
        annotations:
          summary: "No events ingested in 2 hours"

      - alert: OpenAlertsHigh
        expr: threatos_alerts_by_status{status="open"} > 10
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "{{ $value }} open alerts need review"

4. How to Use Event Search, Purple Team, Attack Chains, and Alerts
Event Search — Used for Investigation
Event Search is your forensic tool. You use it after an alert fires to understand what happened.
Scenario: Alert fires — PSExec detected on WIN-SERVER01

Step 1: Go to Event Search
  Host:        WIN-SERVER01
  Time window: Last 24 hours
  → See ALL events from that server

Step 2: Look at the timeline
  09:45  mstsc.exe connects to WIN-SERVER01 from 10.10.10.20
  09:46  PSEXESVC.exe installed
  09:47  cmd.exe /c whoami
  09:47  cmd.exe /c net user /domain
  09:48  cmd.exe /c net user hacker /add

Step 3: Now you have the full attack story
  Attacker IP: 10.10.10.20 (WIN-WORKSTATION01)
  Method: RDP then PSExec
  Actions: Recon then added backdoor account

Step 4: Search for the attacker's source
  Host: WIN-WORKSTATION01
  → See how THEY got access
  → Was there a phishing email?
  → Was there an RDP brute force?
Key Event Search filters:
host         → narrow to one machine
process      → find specific executable (powershell, psexec)
command_line → find specific commands (net user, -EncodedCommand)
user         → find what a specific user did
log_source   → filter by winlog vs syslog
hours_back   → extend window for longer investigations

Purple Team — Used for Validation
Purple Team answers: "If an attacker used this technique right now, would ThreatOS catch it?"
Use case 1: Validate a new rule before trusting it
  POST /api/purple/validate
  {
    "technique_id": "T1059.001",
    "emulated_event": {
      "process": "powershell.exe",
      "command_line": "powershell -EncodedCommand abc"
    }
  }
  
  Result: verdict=pass, detection_rate=100%
  → Your rule works ✅

Use case 2: Test if a known attack would be caught
  Emulate a PSExec attack:
  {
    "technique_id": "T1569.002",
    "emulated_event": {
      "process": "PSEXESVC.exe",
      "file_path": "C:\\Windows\\PSEXESVC.exe"
    }
  }
  
  Result: verdict=pass → caught ✅
  Result: verdict=fail → NOT caught ❌ → fix the rule

Use case 3: Calculate risk before enabling a rule
  POST /api/purple/score
  {
    "severity": 9,
    "confidence": 0.95,
    "asset_criticality": 4,
    "chain_tactic_count": 3,
    "is_multi_stage": true
  }
  
  Result: risk_score=100 (capped)
  → This combination = maximum priority incident

Attack Chains — Used for Incident Detection
A single alert = noise. A chain = an incident.
How to use chains daily:

Step 1: Check the dashboard
  Multi-Stage Chains > 0 → investigate immediately
  
Step 2: For any host with multiple alerts → correlate
  POST /api/chains/correlate
  {"host": "WIN-DC01", "window_hours": 24}
  
Step 3: Read the chain result
  tactics_observed: ["initial-access","execution","persistence"]
  tactic_count: 3
  is_multi_stage: true      ← THIS IS AN INCIDENT
  risk_score: 95

Step 4: Understand the kill chain sequence
  initial-access   → attacker got in (how?)
  execution        → attacker ran code (what?)
  persistence      → attacker planted backdoor (where?)

Step 5: Use Event Search to fill the gaps
  Search host + time window → see every event
  Build the full attack timeline

Step 6: Update chain status
  PUT /api/chains/{id}/status
  {"status": "investigating"}
  → Prevents duplicate work if multiple analysts

Chain risk scoring:
  1 tactic  = isolated event (low urgency)
  2 tactics = related activity (medium urgency)
  3 tactics = confirmed intrusion (high urgency — act now)
  4+ tactics= active APT (critical — escalate immediately)

Alerts — The Daily Workflow
Priority triage (do this every morning):

1. Sort by risk_score descending
   Score 80-100 → Investigate today
   Score 60-79  → Review within 24 hours
   Score 40-59  → Review this week
   Score 0-39   → Background noise

2. For each high-risk alert:

   a) Check the technique
      T1059.001 PowerShell → common, need context
      T1569.002 PSExec     → almost always malicious
      T1558.001 Golden Ticket → CRITICAL, respond now

   b) Check the host
      Is it in Assets? What criticality?
      Domain controller (crit=4) → highest priority
      Dev machine (crit=1)       → lower priority

   c) Correlate the host
      POST /api/chains/correlate {"host": "HOST"}
      Multi-stage result → escalate to incident

   d) Enrich IOCs
      POST /api/ti/enrich-alert/{alert_id}
      MALICIOUS verdict → block IP, isolate host

   e) Search raw events
      GET /api/events/search?host=HOST&hours_back=24
      Build the full story

   f) Make a decision:
      Real threat  → status=investigating → escalate
      False positive → status=false_positive → tune rule
      Benign       → status=closed → document why

3. Weekly alert hygiene:
   → Check noisy rules: GET /api/detection/noisy-rules
   → Disable rules with FP rate > 80%
   → Review rules that haven't fired in 30 days
   → Create rules for techniques that had 0 detections
Alert status lifecycle:
open
  → investigating  (you're looking at it)
      → escalated      (needs incident response team)
      → closed         (resolved — document what happened)
  → false_positive (rule fired incorrectly — tune the rule)
  → closed         (reviewed, benign — document why)

Never delete alerts — they're your audit trail.
Always document why you closed something.
